# Архитектура проекта «Голем»

> **Назначение документа:** рабочий архитектурный паспорт для новых агентов и разработчиков. Он показывает, где находится исходный код, где лежат исследования и как проходят данные через систему.
>
> **Актуальность:** структура сверена с каталогами репозитория на 31 июля 2026 года. Дерево ограничено двумя–тремя уровнями, чтобы оставаться навигационным, а не превращаться в перечень каждого файла.

## 1. Как читать архитектуру

- `docs/` — методологический и операционный контекст. Перед изменением логики сначала ищите соответствующий документ здесь.
- `products/` — прикладные поверхности: сайт, веб-продукты, агенты и экспериментальные системы.
- `tools/` — автоматизация, генераторы, проверки и отчёты. Скрипты могут создавать или обновлять файлы в `docs/`, `products/` и других каталогах.
- `epics/` и `tasks/` — планирование: крупные направления и конкретная работа.
- `archive/` — исторический слой; не использовать как источник актуальной логики без проверки.
- `.github/`, `docker/`, `Dockerfile`, `docker-compose.yml` — доставка и изолированный запуск.

### Research Lab

Research Lab — статический SPA внутри `products/website/`. Это канонический пользовательский интерфейс исследовательских инструментов.

- Технологическая основа: HTML, CSS и Vanilla JavaScript.
- Навигация: hash-routing; маршруты и переходы должны согласовываться с `router.js`.
- Представление: `LabRenderer` и модульные экраны приложения.
- Данные: локальные файлы продукта и результаты генерации из `tools/`.
- Стили: пергаментный интерфейс и продуктовые CSS-файлы.
- Правило: сначала менять исходники в `apps/`, `src/` и связанных папках, затем выполнять сборку; `build/` считать производным слоем.

Для нового агента рекомендуемый порядок чтения:

1. `README.md` в корне — карта возможностей и запуск.
2. `docs/00-START/` — вводный контекст.
3. `docs/03-CONTENT/` — терминология и манифест.
4. `docs/01-ARCHITECTURE/` — границы систем и точки интеграции.
5. `docs/08-EXPOSURE/` и `docs/07-DICTIONARIES/` — предметная модель разоблачения подмен.
6. Документация конкретного продукта в `products/*/` — перед изменением его кода.

## 5. Инструментальный слой: `tools/`

```text
tools/
├── golem.py                # главное CLI-меню
├── golem-config.json       # конфигурация инструментов
├── checkers/               # проверки структуры, имён, ссылок и качества
├── generators/             # генерация индексов, данных, сайта и отчётов
├── reports/                # отчёты о состоянии проекта
├── automation/             # автоматизация рутинных операций
├── sync/                   # синхронизация структуры и changelog
├── analyzers/              # послойная диагностика текстов по методологии
├── lib/                    # общие библиотеки Python
├── utils/                  # вспомогательные преобразования и обслуживание
├── data/                   # служебные данные для скриптов
├── build/                  # промежуточные результаты сборки
└── cache/                  # локальный кэш; не считать каноническим источником
```

Ключевое правило: генераторы и синхронизаторы могут перезаписывать производные файлы. Перед ручной правкой проверьте, не является ли файл результатом работы `tools/generators/` или `tools/sync/`.

## 7. Доставка и изоляция

- `.github/` содержит автоматизацию репозитория и CI/CD.
- `Dockerfile` описывает образ.
- `docker-compose.yml` запускает локальную изолированную среду.
- `docker/entrypoint.sh` — точка входа контейнера.
- `docker/sshd_config` — SSH-конфигурация контейнера.
- `docker/README.md` описывает сеть, секреты, SSH и ограничения безопасности.
- `products/website/build/` — deploy-слой сайта; его следует получать сборкой из исходников.

Docker-свива не является полностью недоверенным sandbox’ом: для LUKS используются расширенные права контейнера. Секреты из `.golem-secrets/` не должны попадать в Git.

## 8. Потоки данных и зависимостей

```text
Пользователь
    ↓
products/website/ (публичный сайт / Research Lab)
    ├── локальные данные и UI-модули
    ├── tools/generators/ → подготовленные данные и индексы
    └── products/agents/ → API и агентные сценарии
                              ├── специализированные агенты
                              └── исследовательская база знаний

docs/ + archive/ + предметные материалы
    ↓ проверка и генерация
 tools/checkers/ + tools/generators/ + tools/reports/
    ↓
products/website/ и отчёты в docs/
```

Основные границы:

- `docs/` — источник методологии и объяснений.
- `products/` — исполняемый код и пользовательские поверхности.
- `tools/` — операции над содержимым и структурой.
- `products/website/build/` и `tools/cache/` — производные состояния.
- `archive/` — исторический контекст, не активная зависимость.

## 9. Точки входа

- Быстрый обзор: `README.md`.
- Главное меню инструментов: `python tools/golem.py`.
- Сайт: `products/website/index.html`.
- Frontend-сборка: `cd products/website && npm run build`.
- Агентный CLI: `python products/agents/main.py "запрос"`.
- Агентный сервер: `python products/agents/server.py`.
- Контейнер: `docker compose up -d --build`.
- Документация: `docs/INDEX.md`.

Команды запуска проверяйте по локальному README и окружению: наличие секретов, API-ключей и зависимостей может быть обязательным.

## 10. Правила для новых агентов

1. Сначала определить, меняется ли методология (`docs/`), продукт (`products/`) или автоматизация (`tools/`).
2. Не создавать новые корневые каталоги без обновления этого документа и `CURRENT_ARCHITECTURE.md`.
3. Не редактировать `build/` и `cache/` как канонические исходники.
4. Перед изменением API или маршрутов проверить документацию продукта и связанные точки входа.
5. После изменений запускать релевантные checker/generator и сверять изменённые ссылки.
6. Секреты, `.env`, ключи и локальные хранилища не коммитить.
7. При обнаружении расхождения между документом и деревом сначала обновить карту архитектуры, затем продолжать работу.
